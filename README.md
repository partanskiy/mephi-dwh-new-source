# Добавление нового источника в DWH

Учебный проект по дисциплине "Работа с данными в хранилище".
МИФИ, магистратура "Высшая аналитика данных", Data Engineering, семестр 3.

Загрузчик объединяет четыре источника маркетплейса товаров ручной работы
в измерения и факты DWH. Инкрементальная витрина
`dwh.customer_report_datamart` содержит одну строку на заказчика и месяц.

**Статус на 13 сентября 2026 года:** SQL-решение реализовано и проверено
на синтетических данных и изолированных копиях 2997 реальных заказов
старых источников. В учебной БД созданы таблица фактов, витрина и журнал
загрузок. Завершающая загрузка четырёх источников ожидает появления
`external_source`: этой схемы в предоставленной БД нет.

## Подключение и запуск

Нужны PostgreSQL client (psql 15 или новее), Python 3.9 или новее,
pass с доступом к GPG-ключу и make. В Arch Linux клиент входит в пакет
`postgresql-libs`.

Параметры хранятся отдельными записями в pass:

```text
MEPhI/semester-3/data-warehouse/host
MEPhI/semester-3/data-warehouse/port
MEPhI/semester-3/data-warehouse/dbname
MEPhI/semester-3/data-warehouse/user
MEPhI/semester-3/data-warehouse/password
```

При другом расположении задайте переменную `MEPHI_PASS_PREFIX`.
Корневой сертификат ожидается в `~/.postgresql/yandex-cloud.crt`;
другой путь задаётся через `PGSSLROOTCERT`. Получить сертификат можно так:

```bash
mkdir -p ~/.postgresql
curl -fSL https://storage.yandexcloud.net/cloud-certs/CA.pem \
    -o ~/.postgresql/yandex-cloud.crt
```

Подключение использует SSL с `verify-full`. Пароль передаётся через
временный файл .pgpass с правами `0600` в закрытой временной директории.
При завершении он удаляется. Значение пароля не передаётся в аргументах
psql, не печатается и не записывается в репозиторий.
Флаг `ON_ERROR_STOP=1` останавливает выполнение при SQL-ошибке.

Команды выполняются из корня проекта:

```bash
make prepare    # создать таблицы и индексы
make load       # загрузить все четыре источника
make refresh    # обновить витрину
make check      # сверить результат с полным расчётом
```

`make run` последовательно выполняет все четыре шага. Пока в учебной БД
нет external_source, шаг load завершится ошибкой без частичной записи
в DWH. После предоставления нового источника нужно сверить его столбцы
с заданием, затем выполнить `make run`.

Для интерактивной работы:

```bash
python3 scripts/psql.py
```

## Правила загрузки

Сохранены бизнес-ключи модели курса:

| Объект | Бизнес-ключ |
|---|---|
| Мастер | Имя и электронная почта |
| Заказчик | Имя и электронная почта; NULL имени обрабатывается явно |
| Товар | Название, описание и цена |
| Заказ | Товар, мастер, заказчик и дата создания |

Идентификаторы источников не считаются глобальными идентификаторами DWH.
Одинаковые представления заказа в разных источниках сводятся к одной
записи по бизнес-ключу. Разные заказы одного источника, попавшие на один
такой ключ, вызывают ошибку: модель курса не позволяет сохранить их
раздельно. Для поддержки этого случая потребуется отдельное отображение
идентификаторов источников в идентификаторы DWH.

Скрипт проверяет потери и размножение строк после соединений, обязательные
значения и противоречия атрибутов. При конфликте версий измерения загрузка
останавливается: источники не содержат времени изменения для выбора
актуальной версии. Заказчики и мастера из отдельных таблиц измерений
загружаются также при отсутствии заказов.

MERGE изменяет load_dttm только при изменении атрибутов. Повторная загрузка
неизменных источников сохраняет строки и их метки времени.

## Расчёт витрины

- Период определяется месяцем создания заказа, формат YYYY-MM.
- Сумма заказчика и средний чек учитывают все статусы, как в примере курса.
  Комиссия платформы равна 10% этой суммы; денежные поля сохраняют копейки.
- Медиана считается по завершённым заказам с известной датой завершения.
  Если таких заказов нет, результат NULL.
- Категория и мастер определяются по числу заказов отдельно за каждый месяц.
  При равенстве выбираются первая категория по сортировке C и минимальный
  идентификатор мастера.
- Имя, адрес и дата рождения заказчика могут быть NULL, как в реальном
  измерении d_customer.

Изменения f_order, d_customer и d_product определяют пары заказчик-месяц
для перерасчёта. Для каждой пары заново читаются **все** её заказы.
Это сохраняет правильные суммы, медиану и рейтинги при позднем заказе
или изменении статуса. Новые пары добавляются через UPSERT по уникальному
ключу `(customer_id, report_period)`.

Граница обработки имеет тип TIMESTAMP, а не DATE, и фиксируется в одной
транзакции с витриной. Блокировки согласуют снимок DWH с загрузчиком;
время пакета берётся после получения блокировок через clock_timestamp().
Оба скрипта используют Europe/Moscow, как исходная учебная БД.

Поддерживаются добавления и изменения неключевых атрибутов. Предполагается,
что история заказов сохраняется, а бизнес-ключи неизменны. Физические
удаления и смена бизнес-ключа, включая цену товара, требуют отдельного
протокола изменений. Сторонний писатель DWH должен обновлять load_dttm
в том же часовом поясе после получения блокировки; изменения с меткой
задним числом не обнаруживаются надёжно без CDC или полного перерасчёта.

## Проверки

```bash
make test       # синтетические регрессионные сценарии
make test-real  # изолированные копии старых источников текущей учебной БД
```

Проверки создают уникальные схемы в подключённой БД и завершаются ROLLBACK;
при ошибке соединение закрывается с откатом. Нужны права создания схем.
Рабочие источники используются только для чтения. В test-real новый
источник пустой, поскольку реального external_source ещё нет.
Синтетический новый источник проверяется отдельно в test.

Проверка make check независимо пересчитывает всю витрину: медиана через
средние элементы отсортированного массива, рейтинги через DISTINCT ON.
Двусторонняя сверка EXCEPT ALL выявляет пропуски, лишние строки и
несовпадения значений. Результаты приведены в
[`docs/validation.md`](./docs/validation.md).
